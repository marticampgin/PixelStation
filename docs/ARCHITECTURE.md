# Architecture

Pixel Station is a local FastAPI application with a React/Vite frontend. The HTTP boundary is ready for a later desktop wrapper without depending on one.

`frontend/src` owns views and accessible controls. `backend/pixel_station` owns routes, deterministic services and provider adapters. `backend/tests` verifies rules and persistence. `config` holds non-secret integration examples. `data` holds databases, uploads, generated artifacts, images and logs and is ignored by Git.

The request workflow is route → retrieve bounded context → execute relevant tools → validate → stream a synthesized answer → persist. Plans and tool permissions are checked by application code. The inference adapter discards separate thinking fields and inline reasoning regions before public streaming or structured validation, including split and unterminated tags. Literal code and JSON-string examples remain content. Gmail sends and Calendar mutations require explicit confirmation of a concrete action; an explicitly requested Gmail draft is saved directly and verified through its returned ID.

Provider interfaces cover inference, embeddings, vision, images, search, web fetch, memory/vector stores, files, email/calendar, tools, games and scheduling. SQLite FTS5 provides lexical search; vector implementation is isolated. Optional integrations can be unavailable without preventing chat or local data management.

Gmail and Calendar share a Desktop OAuth client file but have separate service scopes, account identities, pending OAuth states and OS-keyring token entries. A token for one service cannot be used by the other adapter. Concrete write proposals bind the service and persisted connection generation as well as the exact payload; reconnecting or changing the client requires fresh approval. Token refresh and app restart preserve the generation. Multi-request reads and mutation verification retain the initial binding, so a mid-operation account change cannot redirect follow-up requests.

API conventions: `/api/health`, `/api/models`, `/api/settings`, `/api/conversations`, `/api/memory`, `/api/files`, `/api/web`, `/api/images`, `/api/google`, `/api/poker`, `/api/harness`. IDs are stable strings. Streaming chat uses newline-delimited JSON events with `type` and event-specific fields. Provider failures return setup and recovery information.

Poker's progressive mutations persist the immediate human move. The NDJSON step endpoint commits one opponent decision or street reveal, with public queued/choosing snapshots and a stable event sequence. The client waits its selected reading pace before requesting another step. Table locks and expected sequences reject concurrent or stale actions; navigation cancels unfinished inference and returning resumes the saved actor. Legacy JSON flows retain their automatic-opponent behavior.

Poker judgment uses an allowlisted public view plus the acting player's own hole cards, never opponent pockets, the deck, or future cards. `poker_strategy.py` derives hand/board evidence, position, stack depth, price, and conservative raise/risk guidance. Its 128-sample seeded showdown pot-share estimator assumes uniform random unseen opponents/runouts and split ties among active opponents. It ignores action ranges, fold equity, realization, rake, and side-pot eligibility; it is noisy evidence, not actual win probability or solved EV. Styles supply small nudges subordinate to evidence. `poker.py` allows one structured repair within a whole-decision budget of up to 15 seconds, including evidence, queue waits, and generation, with 180 tokens per attempt. Legality and a separate risk policy validate the action; unavailable or rejected inference uses a disclosed legal fallback. No unbounded inference loop is used.

The watchtower stores content-free per-run metrics in `AgentRun.evidence` and separate passive reports/evaluation jobs in `HarnessReport`. Request-scoped observers collect whitelisted Ollama terminal counters without prompts or reasoning. Diagnostic exports omit private content by default. Passive Poker counts cover newly instrumented production decisions: final selected actions, known native/fallback decisions, and parsed raw attempts/rejections are distinct. A rejected raw all-in can finish as a selected fold. Historical uninstrumented behavior is unknown, and absent samples do not establish quality. Synthetic evaluations stay separate from those production counts.

Every evaluation runs ten deterministic core gates plus six synthetic Poker context/risk gates, for 16 deterministic cases. Native chat's two production-answer probes and Poker's six production-chooser scenarios are independent manual opt-ins, each bounded to 90 seconds (180 seconds across both scopes). Poker PASS requires a legal fixture-acceptable model decision without fallback; repairs and rejected raw actions remain recorded even when the final decision passes. These fixed risk/value criteria do not prove optimal strategy or guarantee that a small model passes. Runner 5 identities include both fixtures, Poker policy version, and decision/context source hashes. Baselines require matching identities, configuration, package versions, and both native scopes; native matching additionally requires a known equal checkpoint digest and Ollama identity. Unknown native identity prevents matching. The scan considers the latest 30 completed evaluations, excluding passive reports. Completion rates do not grade answer correctness, and estimated context tokens remain distinct from native usage. See [EVALUATIONS.md](EVALUATIONS.md) for bounds and evidence interpretation.

Complex research uses a bounded, schema-validated tool DAG. The model supplies two distinct focused queries, or one when only one tool step remains. Application code constructs the step IDs and search/fetch dependencies; a fetch resolves its URL from an actual search result. The model cannot invent a fetch target. Explicit research keeps that route when selected sources are attached; their reads share the configured total tool budget, and their evidence is retained and deduplicated. Query validation permits one repair. Simple chat skips planning. The synthesis call receives one bounded system message containing the selected evidence, which also works with small models whose templates retain only the first system message. Unsupported tool protocol is checked throughout the response and triggers at most one bounded answer retry. A streaming `reset` event clears rejected partial text in both the client and persisted response.

Embeddings use SQLite-vec through an isolated adapter, with a portable cosine fallback. Missing vectors are SQL NULL, allowing the persistent idle indexer to reindex edited content and changed embedding roles. Summaries compact ordered message batches; extraction uses only source user messages and excludes private integration results.

File edits stage and reopen a replacement, bind its exact content and original hash to an expiring single-use proposal, and retain the previous managed copy on confirmation. Gmail sends and Calendar mutations use the same concrete approval principle, plus version checks where available. Draft creation has its own explicitly requested, reversible path. Comfy jobs retain their submission endpoint so subsequent settings changes cannot redirect polling or cancellation.

Comfy jobs serialize through their provider lock and the application's existing inference lock, also used by chat, Poker and idle model work. Fresh Ollama resident-model observations bound an unload-only handoff before Comfy submission. After the owned remote prompt is confirmed inactive, an empty Comfy queue permits `/free`; acknowledgements and observed torch-residency reductions remain distinct recorded facts. Terminal job status is published after bounded cleanup and release observation so the UI receives any warning alongside the saved output. A completed image remains complete when release cannot be confirmed; unknown remote cleanup stays explicit. Other programs using these services are outside the application lock. The 600-second job budget includes queue waits, with up to 30 additional seconds for cleanup/release.

File blobs are immutable and addressed by content hash. Generated artifacts with different requested names have independent attachment records over shared bytes; uploads retain content deduplication. Parse sidecars live under each blob's `records/<attachment-id>` directory, preserving existing legacy sidecars. Editing one record changes only its blob reference and keeps sibling records and revision bytes intact.
